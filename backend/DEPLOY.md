# Deploying the API on Render

The API runs as one Render web service, defined in [`render.yaml`](../render.yaml). The database is MongoDB Atlas.

## First deploy

1. Render dashboard -> **New -> Blueprint** -> connect the GitHub repo -> branch `main` -> **Apply**.
2. Render asks for the secrets (they are never stored in the repo):

   | Variable | Where to get it |
   | --- | --- |
   | `MONGO_URI` | Atlas -> Connect -> Drivers (`mongodb+srv://...`). Must be a replica set (Atlas is) for order transactions. |
   | `CLERK_SECRET_KEY` | Clerk dashboard -> API keys -> Secret key of the **Production** instance |
   | `DELHIVERY_API_TOKEN` | Delhivery One -> Settings -> API and MCP Setup |
   | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_S3_BUCKET_NAME` | AWS IAM user with access to the images bucket |

   `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are generated by Render. With `STRICT_ENV=true` the server will not start
   if `MONGO_URI` or the JWT secrets are missing, instead of silently using the public development defaults.
3. Atlas -> **Network Access**: allow the new service to connect (`0.0.0.0/0`, or the service's outbound IPs from
   Render -> service -> Connect).
4. Check `https://<service>.onrender.com/health` returns `{"success":true,...}`.

## Point the website at it

`frontend/vercel.json` (and the root `vercel.json`) rewrite `/api/*` to the backend. Set the `destination` host to the
service URL (currently `https://vinit-textiles-api.onrender.com/api/$1`), then redeploy the frontend.
Because of the new JWT secrets, everyone (including the admin) has to sign in again once.

## After the first deploy

- **Rate limits and NODE_ENV.** Render's Node runtime sets `NODE_ENV=production` by itself, so the API limit is
  1500 requests / 15 min and `/auth/*` allows 20 / 15 min **per client**. That only works if `req.ip` is the real visitor,
  which depends on `TRUST_PROXY_HOPS` (4 here: browser -> Vercel -> Cloudflare -> Render's load balancer -> app).
  With 1 or 3 the key was a rotating edge address, so visitors would have shared buckets and got 429 errors.
  Re-check it whenever the proxy chain changes (new CDN, different host): send ~70 requests to
  `/api/v1/shipping/serviceability/395012` (limit 60 / 15 min) through `www.vinittextiles.com`; the `RateLimit-Remaining`
  header must count down one by one, the 61st request must return 429, and a burst sent directly to the Render URL
  must share the same bucket from the same machine.
- **Razorpay.** Checkout is Cash on Delivery only. Adding `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET` and
  `RAZORPAY_WEBHOOK_SECRET` switches online payment on by itself. Never set `ALLOW_STUB_PAYMENTS` on a server.
- **Plan.** The free plan sleeps after ~15 minutes without traffic, so the first request is slow. Use **Starter** for a live store.
